# ТЗ для агентов-разработчиков · АгроОкно

> Общий документ для всех агентов. Личные задачи — в `docs/agent-A-data.md` и `docs/agent-B-ui.md`.

## 1. Цель продукта

Мобильная платформа «АгроОкно» для фермеров Республики Саха (Якутия): **«Один раз ввел — везде сдал»**.
Фермер (глава КФХ / ИП) или владелец ЛПХ один раз вносит события хозяйства (приплод, падёж, забой, продажа, надой, заготовка кормов, урожай), а приложение само готовит:

- формы отчётности КФХ/ИП для **Росстата** и **Минсельхоза России** (бланки в `C:\AgroOkno\ТЗ`): 1-фермер, 2-фермер, 3-фермер, 1-КФХ, 1-ИП;
- **ежемесячную версию 3-фермер** (Сахастат прекращает республиканские формы);
- республиканские формы Сахастата: 1-ТАБУН, 10-СХ, 1-ИСО-р (официальных бланков нет — только превью в приложении);
- данные для компонента **«Меркурий» ФГИС ВетИС** (реализация продукции животноводства, факт перемещения);
- **похозяйственную книгу** ЛПХ (члены хозяйства, участок, скот, выписка PDF).

Источник: письмо ГКУ «РЦПТ РС(Я)» от 22.10.2026 № 987/574 (`ТЗ/155950111.pdf`), кейсы 1 и 2. Приказы и бланки: `ТЗ/*.XLSX`, `ТЗ/Минсельхоз России приказ 165.pdf`, `ТЗ/Похозяйственная книга *.pdf/.xlsx`, `ТЗ/Сахастат приказ формы.pdf` (130 МБ — читать постранично).

Отчёты **не хранятся** — всегда вычисляются из событий за период. Отправка в ведомства и Меркурий — **демонстрационная** (квитанции генерируются у нас, внешних интеграций нет; все такие места помечены в UI плашкой «учебные данные», как в макете).

## 3. Стек (уже в `C:\AgroOkno\app`)

- Expo SDK 58, Expo Router (маршруты в `src/app/`), React 19.3, React Native 0.88, React Compiler, typed routes.
- Supabase (`@supabase/supabase-js`), клиент — `src/lib/supabase.ts`.
- expo-sqlite (локальная БД; на вебе — wasm, заголовки COOP/COEP уже в `metro.config.js` и `vercel.json`).
- Vercel: веб-сборка `npx expo export -p web` (SPA) + serverless-функции `app/api/**` (Node, exceljs). Бланки — `app/templates/`.
- Миграции — `C:\AgroOkno\supabase\migrations\`.

**Обязательно перед кодом:** прочитать `app/AGENTS.md`. Expo меняется каждую версию — сверяться с https://docs.expo.dev/versions/v58.0.0/ и https://docs.expo.dev/llms.txt, не писать по памяти. Зависимости — только `npx expo install <pkg>` (в `C:\AgroOkno\app`). Node-only код (exceljs, pdf-lib) — только в `app/api/**`, чтобы Metro его не бандлил.

### Образцы, которые надо переиспользовать
- `app/src/reports/fermer3.ts` — чистый маппер событий → строки формы (без RN-зависимостей; общий для приложения и API).
- `app/api/reports/3-fermer.ts` — Vercel-функция: проверка параметров, Supabase-клиент от имени пользователя (RLS), вызов маппера, отдача XLSX.
- `app/api/_lib/fermer3-xlsx.ts` — заполнение оригинального бланка через exceljs по адресам ячеек.
- `supabase/migrations/20261023000000_init.sql` — стиль схемы: клиентские uuid, `updated_at` через moddatetime, `deleted_at` (мягкое удаление), RLS через `owns_farm()`.

## 4. Контракт между слоями — `app/src/data/contract.ts`

Единственная точка стыковки UI и данных. Типы сущностей + интерфейс `DataModule` (все хуки).
- UI импортирует хуки **только** из `@/data`, типы — из `@/data/contract`.
- `src/data/index.ts` проверяет на этапе компиляции, что реализация соответствует `DataModule`. Сейчас он реэкспортирует `./mock` (моки агента B); агент A переключает его на реальную реализацию в конце.
- Менять контракт можно только **аддитивно** (новые необязательные поля, новые хуки) с записью в `docs/CONTRACT-CHANGES.md` (дата, что, зачем). Переименование/удаление — запрещено.

### Сквозные UX-правила
1. Каждая форма ввода события и детали события содержат блок **«Куда попадут данные»** (из `getEventDestinations`) и подпись «Данные обновятся после сохранения. Отчеты отправляются только после вашей проверки и подтверждения».
2. Отчёт уходит только после экрана подтверждения (C6) с чекбоксом «Данные проверены». Уже отправленные отчёты задним числом не меняются.
3. Удаление — только через модалку H2 с перечнем последствий.
4. Офлайн: всё сохраняется локально; отправка отчётов недоступна; жёлтая плашка «Вы офлайн. Данные из кеша на …» (G2). Первая загрузка без кеша — skeleton (G1).
5. Демо-места (ЕСИА, отправка отчётов, Меркурий, SMS/email-коды в демо) помечены info-плашками, как в макете.

## 6. Доменная модель (кратко; точные типы — в контракте)
Profile (role, реальный email/телефон) · Farm (legal_status kfh/ip/lph, ИНН/ОГРН/ОКПО/ОКТМО, регион, населённый пункт, адрес, глава, № записи книги, кадастровый №, площадь участка) · HouseholdMember · события: LivestockEvent, ProductOutputEvent, ProductSaleEvent, FeedEvent, CropEvent · ReportSubmission (form_code, period, status, receipt_no) · ReportDeadline (справочник сроков) · MercuryConnection / MercuryDocument · AppNotification · UserSettings · SupportTicket.

Демо-данные (seed) — как в макете: «ЛПХ Ивановых», с. Намцы, ул. Луговая, 12, запись книги № 0142, кадастровый № 14:18:010001:1248, участок 2 500 кв.м; члены: Иван Иванов (глава), Мария Иванова (супруга), Алексей Иванов (сын); скот: коровы 15, телята 8, лошади 32 (18 кобыл, 10 молодняк, 4 жеребца), овцы 24; надой за октябрь 1 200 л; табун: на 1 октября 29, +6 родилось, −1 пало, −2 забито. Демо-вход: ИНН `143512345660` (пароль задать и указать в итоговом отчёте) → рабочее пространство «ЛПХ Ивановых»; список обязательств как в макете (федеральные 10-СХ, 1-ИП, 1-ИСО-р; республиканские 1-ТАБУН, 3-фермер (рег)). Одна учётная запись = одно хозяйство. Второй демо-аккаунт — КФХ (свой 12-значный ИНН) с событиями за 2025–2026 для годовых форм 1/2/3-фермер, 1-КФХ. ИНН проверяется только по формату (10 или 12 цифр), без контрольной суммы — учебные ИНН должны проходить.
